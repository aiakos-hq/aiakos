# Story review: slice 10-5

Reviewed at commit bd5f981. Stories: 8. Check: ok.

## Findings

- [x] S2 (context-gap): E2 ("one seq; buffered replay same bytes/seq/trace") and E3 (STOPPED, SEAT_STOPPING and COMMAND_TIMEOUT results) need a result in NodeEventBuffer, but how a terminal result enters the buffer (seat and launch, ObservedAt, SourceSeq=0, seat registered first, minimal inventory for an unknown seat) is the end of R4, owned by S4, and neither `depends` nor `notes` of S2/S3 names it. Fix: move those sentences out of R4 into R2 (or an item S2 owns), so S4 does not change what S2 and S3 already emit.
- [x] S2 (context-gap): R2 says a malformed ID is "translated by the stream to FailedPrecondition", but S2 does not touch the stream, R5/E5/T5 do not mention it, and today an ArgumentException from `ReceiveAsync` ends in the generic catch of `OrchestratorConnection.cs:118` as Unavailable. Fix: move the translation into R5 and add it to E5, leaving only the local throw in R2.
- [x] S4 (context-gap): R3 rejects an absent or nonpositive Timeout with INVALID_LAUNCH and R4 says the first CommandValidator error wins "before seat preconditions"; for a command with both an invalid timeout and a validator error the brief does not say which result is emitted. Fix: state the order of the timeout check, the validator and the seat preconditions in R4 and add that input to E4.
- [x] S4 (context-gap): R4 answers a StartSeat for a different live LaunchId, the same Ready launch and the same pending launch, but not for the same LaunchId that is registered, not pending and not Ready: finished Failed/Unknown in this process, or registered with Ready=false by the adoption producer after a node restart, which R7 reaches by resending StartSeat with the same LaunchId to a changed node instance; nor does it say whether a different LaunchId on a Failed/Unknown occupied seat counts as "live". Without an answer an implementer may call the driver again and launch twice. Fix: give the exact status, reason and Launch body for both inputs in R4 and add them to E4 and T4.
- [x] S4 (context-gap): R4 says the same active launch returns "Completed Launch Ready" without a driver call, but not what the rest of that LaunchResult holds (reason, observed_session_id, evidence), while the pending case says "copy its outcome". Fix: say in R4 whether the Ready case copies the original result or returns a LaunchResult with only the outcome set.
- [x] S1 (context-gap): R1 clones a NodeCommandSeat "into NodeEventBuffer" and R4 registers a "minimal seat inventory (empty launch/native/harness)", but SeatInventory has no harness field and the brief gives no value for `lifecycle` or `native_session_id` in either case, nor says whether registering again replaces values the adoption producer set. Fix: give the exact SeatInventory field values for RegisterSeat, for a start-registered seat and for the minimal inventory, and say that an existing inventory's other fields are kept or replaced.
- [x] S1 (context-gap): R1 forbids overwriting "an active seat's launch on a different StartSeat until the driver has returned Ready" and R4 puts the "known launch" on each result, so for a StartSeat with a new LaunchId on a stopped seat that ends Failed, Unknown or TimedOut the brief does not say which launch id is on the result event and in the inventory. Fix: define "active" and state the launch id of the result and of the inventory for that input in R4 (R1 for the registration part).
- [x] S6 (context-gap): R6 changes the registry from the key `identity.NodeId` (`NodeLinkRegistry.cs:23`) to tenant and node name without a `C` item, and `NodeTokenRegistry` only requires unique ids and tokens, so two registered nodes may share tenant and name; the brief gives no answer for both being connected (which one is the target, does one supersede the other). Fix: add a `C` item that says what stays keyed by NodeId and what a tenant/name lookup returns when two sessions match, with that input in E6.
- [x] S6 (context-gap): R6 says the ack timeout is "command Timeout from admission" and that the slot is released "after outer command timeout", which is the same instant, so "sent-but-unacked command remains tracked until final result/timeout/reconnect decision" has no interval in which it applies and an implementer must guess whether there are two deadlines. Fix: say in R6 that it is one deadline and what SendAsync returns and what the tracker holds when it expires, or name the second deadline.
- [x] S4 (context-gap): R4 is too large for one run: validation order, seat preconditions of five kinds, the launch state (pending same launch, occupancy until stop), busy and lead checks, capture truncation at a scalar boundary, driver error mapping and result registration, all behind the single row E4. Fix: split R4 and E4/T4 into a launch and stop rule (StartSeat, StopSeat, occupancy) and an input and capture rule (DeliverInput, SendKeys, CapturePane), each its own story.
- [x] S8 (context-gap): S8 joins the adapter and loopback proof, which need only the 13-4 protocol story and 10-4, with the real actor proof, which needs the 13-3 and 13-4 production stores (16 stories of 13-4 are not merged), so the adapter cannot be readied until all of 13-4 exists. Fix: split R8/E8/T8 into the adapter with the loopback proof and the real actor proof, each story naming only its own external prerequisites.
